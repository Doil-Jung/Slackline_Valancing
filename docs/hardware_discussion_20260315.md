## 1. 상태증강 모드 버그 발견 및 수정

### 🧑‍💻 나의 요청
> 상태 증강 모드로 들어가면 제어가 잘 되는게 아니라 시뮬레이션 실행이 안되고 버튼이 먹통이 되어 있더라고.

### 🤖 AI 분석 & 수정
AI가 코드를 분석한 결과, `lqr.js`의 `setDelay()` 함수에서 `uPipeline`을 `Float64Array`로 생성했는데, `_computeAugmented()`에서 `.push()`와 `.shift()`를 호출하고 있었음. **`Float64Array`는 이 메서드들을 지원하지 않아** `TypeError`가 발생하고, `requestAnimationFrame` 루프가 죽어서 시뮬레이션이 멈추는 현상이 발생했음.

수정 내용:
```diff
-this.uPipeline = new Float64Array(this.actuatorDelaySteps);
+this.uPipeline = new Array(this.actuatorDelaySteps).fill(0);
```

AI가 브라우저에서 검증까지 진행:
- ✅ 상태증강 LQR 모드 전환 시 시뮬레이션 정상 작동
- ✅ 지연시간 50ms 설정 후 안정적 제어 (16차원 상태증강)
- ✅ 교란 적용 시 정상 반응
- ✅ 기본 LQR ↔ 상태증강 LQR 모드 전환 정상

## 2. 게인 스케일의 의미

### 🧑‍💻 나의 질문
> 상태증강모드로 하니 게인 2.0으로 높이니 65ms 까지 제어 된다. 게인의 의미가 뭐야?

### 🤖 AI 답변
LQR 제어기의 출력에 단순 곱셈 스케일링을 적용하는 것:

**τ_actual = gainScale × (−K · x)**

| 게인 스케일 | 의미 |
|:---:|---|
| **1.0** | DARE가 계산한 이론적 최적 게인 그대로 사용 |
| **< 1.0** | 소극적 반응 → 부드럽지만 느린 복원 |
| **> 1.0** | 공격적 반응 → 빠른 복원, 진동 위험 |
| **2.0** | 최적 토크의 2배 힘으로 즉시 반응 |

지연이 있으면 제어기가 과거 정보로 판단하므로 이론적 최적 게인(1.0)으로는 힘이 부족. 게인을 올리면 더 강한 반응으로 보상하지만, 너무 올리면 과보정 → 진동 → 발산.

## 3. 실제 로봇에서의 게인 적용

### 🧑‍💻 나의 질문
> 음 게인 2 이면 실제 로봇에서는 어떻게 적용되는거야?

### 🤖 AI 답변
게인 2.0은 실제로:
- 모터 출력 2배 (같은 기울기에 대해 모터가 2배 세게 돌아감)
- 전류 소모 2배 (토크 ∝ 전류)
- 기계적 부하 증가 (관절, 기어, 프레임에 2배 응력)

실무에서는 게인 스케일 단순 곱셈보다 Q/R 재튜닝, 상태 예측기(Observer), H∞ 제어 등 더 나은 방법을 사용.

## 4. 게인을 높이면 왜 최적이 아닌가

### 🧑‍💻 나의 질문
> 그럼 게인을 높여서 제어가 잘 되는데 왜 그게 최적 상수가 아닌거야?

### 🤖 AI 답변
LQR에서 "최적"의 진짜 의미: 비용함수 **J = Σ(xᵀQx + uᵀRu)** 를 최소화.

"균형을 잡느냐 못 잡느냐"가 아니라 **"상태 오차(기울기)"와 "제어 노력(토크)"의 가중합을 무한 시간 동안 최소화"**하는 것.

| | 게인 1.0 (최적) | 게인 2.0 |
|---|---|---|
| 균형 잡는가? | ✅ 잡음 | ✅ 더 빠르게 잡음 |
| 토크 크기 | 적절 | 4배 에너지 소모 (τ² ∝ 4배) |
| 비용 J | **최소** ✨ | 더 큼 |

비유: 자전거를 탈 때 핸들을 **살짝** 틀어서 복원하는 것(게인 1.0)과 **확** 꺾어서 복원하는 것(게인 2.0) — 둘 다 안 넘어지지만 전자가 "최적".

## 5. 하드웨어 한계와 우선순위

### 🧑‍💻 나의 의견
> 그러면 로봇으로 구현한다고 했을 때 게인을 높여도 전기, 기계 부품의 한도를 넘어가지만 않으면 괜찮은거네. 일단은 효율보다는 균형을 잡는 것에 집중하고 있거든.

### 🤖 AI 답변
맞습니다. 확인할 것:
- 모터 최대 토크/회전속도 내인지
- 전류 한계 초과 여부
- 기어 강도 (순간 토크에 기어 이가 버티는지)

프로토타입 접근법:
1. **일단 균형부터 잡기** ← 지금 여기
2. 하드웨어 한계 내에서 게인 올려서 안정 영역 확보
3. 균형 확인 후 Q/R 튜닝으로 효율 개선

## 6. Q와 R의 의미

### 🧑‍💻 나의 질문
> Q 와 R이 뭐더라? 균형과 노력 이었나?

### 🤖 AI 답변
- **Q** = 상태 오차 페널티 — "얼마나 빨리 균형으로 돌아와야 하나"
- **R** = 제어 노력 페널티 — "토크를 얼마나 아껴야 하나"

현재 시뮬레이터 설정:
```
Q = diag(1, 50, 50, 0.1, 5, 5)
R = 0.001
```

| Q 인덱스 | 상태 | 값 | 의미 |
|:---:|---|:---:|---|
| Q₁ | φ (발 위치) | 1 | 발이 좀 움직여도 괜찮음 |
| Q₂ | α (하체 기울기) | 50 | 하체 기울기는 중요! |
| Q₃ | θ (상체 기울기) | 50 | 상체 기울기도 중요! |
| Q₄ | φ̇ (발 속도) | 0.1 | 발 속도는 덜 중요 |
| Q₅ | α̇ (하체 각속도) | 5 | 각속도도 신경 씀 |
| Q₆ | θ̇ (상체 각속도) | 5 | 각속도도 신경 씀 |

R=0.001로 매우 작으니, 이미 "균형 우선, 효율 나중" 전략.

## 7. 하드웨어 지연시간 현실성

### 🧑‍💻 나의 질문
> 지금 60ms 정도면 우리가 실제 하드웨어로 구현했을 때 지연속도와 비슷하거나 짧아 보이는데 어떻 것 같아?

| 통신 (I2C/SPI) | 0.5~2 ms |
| 제어 연산 (MCU) | 0.1~5 ms |

## 8. 로봇 크기 및 구성

### 🧑‍💻 나의 설명
> 로봇의 크기가 대략 상하체 합쳐서 40cm 정도 이내이면 좋겠어. 전람회 전시 규격이 높이 60cm 이거든 바닥에서 약간 띄운 줄 위에서 실제로 줄을 잘 타는 로봇을 만들고 싶어. 상체 하체 아크릴이나 3D 프린터로 몸체를 만들고 힙관절에 서보 모터를 붙이고 상체에 보드와 배터리를 넣을까 하는데 가능하려나 모르겠어.

### 🤖 AI 답변

| 부품 | 추천 | 가격대 |
|---|---|:---:|
| MCU | ESP32-S3 | ~5천원 |
| IMU | MPU6050 (DMP 모드) | ~2천원 |
| 서보 | MG996R 또는 DS3218 | ~8천원 |

200g 로봇이면 필요 토크가 매우 작아서 MG996R 하나면 충분. ESP32 + MPU6050 조합이면 지연 15~30ms 가능.

## 9. 무게 분포와 막대 모델의 타당성

### 🧑‍💻 나의 우려
> 배터리와 보드와 센서와 전선들이 들어갈 거라서 상체 무게가 꽤 추가 될 것 같고 그 상태에서 균형을 잡으려면 로봇이 조금 더 커야 하지 않을까 짐작해.

### 🤖 AI 답변
작은 로봇이 유리한 점도 있음:
- 관성 모멘트 ∝ mL² → 크기 작으면 관성이 급격히 줄어듦
- 작은 토크로도 빠르게 교정 가능
- 40cm, 200g이면 MG996R 토크로 충분

### 🧑‍💻 나의 질문
> 서보는 관절쪽에 붙어 있고 배터리는 머리쪽에 넣는 방법으로 가능한한 균등 분배하면 막대기로 가정한 시뮬레이션 결과도 크게 틀리진 않겠지?

### 🤖 AI 답변
거의 맞음. 양끝에 무게를 분배하면:
- CoM 위치: 거의 중앙 ✅ (균일 막대와 유사)
- 관성 모멘트: 양끝 집중(아령 효과)으로 mL²/12보다 약 1.5~2배 커짐 ⚠️
- 하지만 넘어지는 속도도 느려지므로 두 효과가 어느 정도 상쇄
- LQR 게인 튜닝으로 충분히 보상 가능

## 10. 줄 타기 물리학 — 원호 반지름 R

### 🧑‍💻 나의 질문
> 줄이 늘어나지 않고 줄을 잡아주는 고정점이 흔들리지 않아야 한다는 가정이 있어야 궤적이 원호가 되는데. 알루미늄 프로파일로 기둥을 만들고 낙시줄(합사) 정도로 하면 괜찮을까? 원호 반지름 R은 줄길이와 기둥사이의 거리로부터 피타고라스 정리로 계산되는 처진 길이가 되는것도 맞지?

### 🤖 AI 초기 답변 (오류 포함)
AI가 "발이 줄 위를 미끄러지며 궤적이 원호"라고 잘못 설명.

### 🧑‍💻 나의 정정
> 네가 아직 상황을 이해 못했구나. 처짐 위치에서 줄 위를 발이 미끄러지는게 아니라 줄과 수직한 단면에서 줄과 발이 함께 흔들리는 거야.

### 🤖 AI 수정된 답변
맞는 지적. 올바른 이해: 발이 줄 위 한 점에 고정된 채로, **줄과 함께 좌우로 (줄 방향에 수직으로) 흔들림**.

```
  기둥──── 줄 ────기둥
    \              /
     \     h      /
      \   ↕     /
       \  ↙↘  /     ← 줄과 발이 함께 좌우 흔들림
        \/
```

발의 궤적을 수학적으로 유도하면 **반지름 h인 원호**:

**R = h = √((L_s/2)² − (d/2)²)**

피타고라스 정리로 계산한 처짐 길이가 곧 원호 반경 R. ✅

재료:
- 기둥: 2020 알루미늄 프로파일 — 흔들림 없음 ✅
- 줄: 합사 낚싯줄 (신축률 ~3%) — 늘어남 거의 없음 ✅

## 11. 줄 위 비율 설정

### 🧑‍💻 나의 의견
> 기둥 간격 60cm 에 R=30cm 정도는 되는게 지금 비율과 비슷해 보여.

### 🤖 AI 확인

| | 시뮬 기본값 | 로봇 실물 |
|---|:---:|:---:|
| 몸체 높이 | 1.65m | 0.40m |
| R | 1.50m | 0.30m |
| R/몸체 | 0.91 | 0.75 |

R=30cm이면 필요한 줄 길이:
```
L_s = 2 × √(R² + (d/2)²) = 2 × √(30² + 30²) ≈ 85cm
```

## 12. 발 형태 설계 — 앞뒤 구속 문제

### 🧑‍💻 나의 질문
> 지금도 v홈이나 원형홈 또는 원형 고리를 생각하고 있는데 그게 앞뒤 움직임을 잘 잡아줄 수 있을까?

### 🤖 AI 비교

| 방식 | 좌우 구속 | 앞뒤 구속 |
|---|:---:|:---:|
| V홈 | ✅ | ❌ 미끄러짐 |
| 원형 홈 | ✅ | ❌ 미끄러짐 |
| **원형 고리** | **✅** | **✅ 줄이 관통하므로 이탈 불가** |

원형 고리 추천 — 줄이 고리를 관통하므로 앞뒤 이탈 불가.

### 🧑‍💻 나의 아이디어
> 앙 고리를 달고 필요하면 줄에 고무링 같은 것을 고리의 앞 뒤에 붙여서 앞뒤 움직임을 더 막을 수 있겠구나

### 🤖 AI 동의
```
기둥 ●━━━━━◉━━[O]━━◉━━━━━● 기둥
              고무링  고리  고무링
```
- 좌우 흔들림만 자유 (시뮬의 φ 자유도와 정확히 일치)
- 고무링 위치 조절로 줄 위 정확한 위치 고정 가능
- 순간접착제로 고무링 고정하면 완벽

## 14. 왜 막대 위에서는 테스트 불가한가

### 🧑‍💻 나의 지적
> 방금 전에 막대위에서 세우기를 먼저 하라고 했는데 우리 알고리즘으로는 막대위에 세울 수는 없어. 서핑 메커니즘의 기본이 발이 움직여야 하는데 막대는 움직이지 않으니까

### 🤖 AI 수긍
맞는 지적. 시뮬레이터의 균형 원리:

```
힙 토크 τ → 상체/하체 반작용 → 발이 원호 위를 이동(φ) → CoM이 발 위로 복원
```

**발의 이동(φ)이 균형의 핵심.** 힙 토크 자체가 CoM을 직접 잡는 게 아니라, 힙 토크의 반작용으로 발이 몸의 무게중심 아래로 이동하는 것이 균형 원리.

막대 위에서는 φ 고정 → CoM 복원 수단 없음 → 제어 불가.

따라서 **바로 줄 위에서 테스트해야 함.**
